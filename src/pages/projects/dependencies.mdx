## Dependencies

Foundry uses git submodules to manage dependencies. Libraries are stored in `lib/` and imported via remappings.

### Installing dependencies

:::code-group

```bash [Basic]
$ forge install OpenZeppelin/openzeppelin-contracts
```

```bash [Specific version]
$ forge install OpenZeppelin/openzeppelin-contracts@v5.0.0
```

```bash [With commit]
$ forge install OpenZeppelin/openzeppelin-contracts --commit
```

:::

The library is cloned to `lib/openzeppelin-contracts/`.

### Locking dependencies

For dependencies installed as git submodules, Foundry maintains a `foundry.lock` file in the project root. The lock file complements `.gitmodules`: `.gitmodules` records where each submodule comes from, while `foundry.lock` records whether you selected a branch, tag, or revision and the resolved commit.

For example, a dependency installed from a tag produces an entry like this:

```json
{
  "lib/openzeppelin-contracts": {
    "tag": {
      "name": "v5.0.0",
      "rev": "b7954c3e9ce1d487b49489f5800f52f4b77b7351"
    }
  }
}
```

Commit `foundry.lock` so other contributors and CI use the same dependency state. Let Forge update the file instead of editing it manually:

- `forge install` creates or synchronizes the lock file. With no dependency arguments, it also installs existing submodules from the recorded state.
- `forge update` updates branch-based dependencies to the latest commit on their recorded branch. Dependencies installed from a tag or revision stay pinned unless you explicitly select a different ref.
- `forge remove` removes the dependency's lock-file entry.
- `forge build` warns if the lock file is malformed, a dependency is missing, or its checked-out revision does not match the lock file.

Dependencies installed with `forge install --no-git` are regular directories rather than git submodules, so Foundry does not add them to `foundry.lock`.

### Using dependencies

Import installed libraries in your contracts:

```solidity
import {ERC20} from "openzeppelin-contracts/contracts/token/ERC20/ERC20.sol";
```

Foundry automatically creates remappings for libraries in `lib/`. The remapping `openzeppelin-contracts/` points to `lib/openzeppelin-contracts/`.

### Remappings

Customize import paths with remappings in `foundry.toml`:

```toml
[profile.default]
remappings = [
    "@openzeppelin/=lib/openzeppelin-contracts/",
]
```

Now you can import with the prefix:

```solidity
import {ERC20} from "@openzeppelin/contracts/token/ERC20/ERC20.sol";
```

#### Nested dependency remappings

When a dependency remapping points below an auto-detected package root, Foundry preserves both by
scoping the dependency remapping to the directory that declares it. For example, `forge remappings`
can output:

```txt
lib/outer/:inner/=lib/outer/lib/inner/contracts/
inner/=lib/outer/lib/inner/
```

The contextual form `<context>:<name>=<target>` applies to imports made by source units whose names
begin with `<context>`. Here, the trailing slash in `lib/outer/` creates a directory boundary, so
sources inside `lib/outer/` use the dependency's `contracts/` directory while root sources and
sibling dependencies use the auto-detected package-root mapping.

#### Dependency remapping scope

Dependencies can declare remappings in their own `foundry.toml` or `remappings.txt`. A declaration
without a context stays global, so your root project and other dependencies can use it, as long as
its alias is unique. Declarations that resolve to the same target can also share an alias.

Foundry scopes a dependency's declaration to that dependency when the alias is ambiguous:

- Another dependency declares the same alias with a different target.
- The alias conflicts with an auto-detected package or one of your project paths.

Each dependency then compiles against its own target. Foundry 1.9 and earlier instead picked one of
the conflicting declarations and applied it to the whole project, including inside the other
dependencies. For example, `permit2`, `v4-core`, and `v4-periphery` each declare `solmate/` at a
different commit, and Foundry 1.9 silently compiled all three against `permit2`'s copy.

When scoping removes the target an alias used to resolve to, Foundry prints a warning such as:

```txt
Warning: Dependency remapping `@openzeppelin/contracts/=lib/openzeppelin-contracts/contracts/` now applies only within `lib/openzeppelin-contracts/`. Imports of `@openzeppelin/contracts/` from the root or other dependencies may resolve differently. ...
```

Review this warning even if your build succeeds: your root sources, or another dependency that
declares the same alias, may now compile against a different version. Foundry does not warn when
the same target remains globally available or when a root remapping already sets the alias.

Dependencies installed outside your project root, such as through `libs = ["../shared"]`, and
dependencies whose configured `src` resolves outside their package directory keep their previous
declaration scope.

#### Root remappings take precedence

Remappings from your root `foundry.toml`, `remappings.txt`, `FOUNDRY_REMAPPINGS`, and `--remappings`
override dependency declarations everywhere, including in source files inside dependencies:

- A root remapping without a context, for an equal or broader alias, replaces every dependency's own
  declaration of that alias.
- A narrower root alias overrides only its matching import subtree, and the dependency's declaration
  handles the remaining imports.
- A root remapping with a context applies as written. The longest matching context wins, so a
  `<dependency>/:` remapping takes precedence over a root remapping without a context inside that
  dependency.

You can therefore choose how an ambiguous alias resolves:

- **Restore the Foundry 1.9 resolution:** add the remapping that the warning suggests to your root
  remappings. Every source in the project, including other dependencies, uses that target, and the
  warning goes away.
- **Keep a dependency's own copy:** also add a context remapping for that dependency,
  `<dependency>/:<alias>=<target>`, using the target from the dependency's own remappings,
  relative to your project root.

#### Example: two copies of OpenZeppelin Contracts

Consider a project that installs OpenZeppelin Contracts 5.x and a testing library, `properties`,
that ships its own OpenZeppelin Contracts 4.8.0:

```txt
lib/
├── openzeppelin-contracts/          # 5.x, declares @openzeppelin/contracts/
└── properties/
    ├── contracts/
    └── lib/
        └── openzeppelin-contracts/  # 4.8.0, also declared as @openzeppelin/contracts/
```

Both dependencies declare `@openzeppelin/contracts/` with different targets, so Foundry scopes each
declaration to its owner and warns that
`@openzeppelin/contracts/=lib/openzeppelin-contracts/contracts/` now applies only within
`lib/openzeppelin-contracts/`. Even if your root sources never import `@openzeppelin/contracts/`,
`properties` now compiles against its own 4.8.0 copy instead of 5.x, which changes its artifacts.

To compile everything against 5.x, as Foundry 1.9 did, add the suggested remapping to your root
`remappings.txt`:

```txt [remappings.txt]
@openzeppelin/contracts/=lib/openzeppelin-contracts/contracts/
```

To use 5.x everywhere except in `properties`, which keeps 4.8.0, add a context remapping for it as
well:

```txt [remappings.txt]
@openzeppelin/contracts/=lib/openzeppelin-contracts/contracts/
lib/properties/:@openzeppelin/contracts/=lib/properties/lib/openzeppelin-contracts/contracts/
```

Both options silence the warning. Run `forge remappings` to check the resulting remappings.

### Updating dependencies

Use `forge install` to add a dependency or initialize the dependencies already recorded in a checkout. Running it without arguments reconciles existing git submodules and `foundry.lock`; it does not intentionally fetch newer dependency revisions.

Use `forge update` when you want to move a dependency to a different revision. With no arguments, it fetches the latest commit for every branch-based dependency:

```bash
$ forge update
```

Dependencies installed from a tag or commit revision remain pinned during a plain `forge update`. To upgrade one of them, provide the new ref explicitly. For example, to move OpenZeppelin Contracts from `v5.0.0` to `v5.1.0`:

```bash
$ forge update openzeppelin/openzeppelin-contracts@tag=v5.1.0
```

You can also select a branch or an exact commit with `@branch=<NAME>` or `@rev=<COMMIT>`. Forge updates the dependency's git submodule checkout and its `foundry.lock` entry together.

Review and commit both the changed dependency path and `foundry.lock` after an update.

See the [`forge install`](/reference/forge/install) and [`forge update`](/reference/forge/update) references for all options.

### Removing dependencies

```bash
$ forge remove openzeppelin-contracts
```

This removes the submodule from `lib/` and `.gitmodules`.

For Git submodules installed by `forge install` in a project at the root of an ordinary Git checkout, a successful `forge remove` performs these cleanup steps for each dependency:

- runs `git rm`, which deletes the dependency's directory from `lib/` and its entry from `.gitmodules`
- deletes the dependency's directory under `.git/modules/`
- removes the dependency's `submodule.*` section from `.git/config`
- removes the dependency's entry from `foundry.lock`

If your Foundry project is nested below the Git root, check `foundry.lock` for a stale dependency entry after removal. Linked Git worktrees use a different Git directory layout, so the cleanup may fail before all steps complete.

#### Resolution strategies

**1. Use a compatible version**

Find a version that works for both dependencies:

```bash
$ cd lib/conflicting-library
$ git checkout v2.0.0
$ cd ../..
$ git add lib/conflicting-library
$ git commit -m "Pin conflicting-library to v2.0.0"
```

**2. Create separate remappings**

If dependencies need different versions, install both under different names:

```bash
$ forge install library-v1=org/library@v1.0.0
$ forge install library-v2=org/library@v2.0.0
```

Add remappings:

```toml
[profile.default]
remappings = [
    "library-v1/=lib/library-v1/",
    "library-v2/=lib/library-v2/",
]
```

**3. Patch the dependency**

Fork and modify the dependency to use a compatible version:

```bash
# In lib/problematic-dependency
$ git remote add fork https://github.com/you/fork
$ git fetch fork
$ git checkout fork/compatible-branch
```

### Using npm packages

Foundry can use packages from `node_modules`:

```toml
[profile.default]
libs = ["lib", "node_modules"]
```

Install with your preferred package manager:

```bash
$ npm install @openzeppelin/contracts
```

Import directly:

```solidity
import {ERC20} from "@openzeppelin/contracts/token/ERC20/ERC20.sol";
```

:::warning
npm packages may not be designed for Foundry. Prefer git submodules for Solidity libraries.
:::

### Hardhat compatibility

For projects migrating from Hardhat or using Hardhat-style imports:

```toml
[profile.default]
libs = ["lib", "node_modules"]
remappings = [
    "@openzeppelin/=node_modules/@openzeppelin/",
    "hardhat/=node_modules/hardhat/",
]
```
